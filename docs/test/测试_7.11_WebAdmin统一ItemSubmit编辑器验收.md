# 测试_7.11_WebAdmin统一ItemSubmit编辑器验收

## 目标

验证 7.11 WebAdmin unified itemSubmit requirement list editor 是否正确取代 7.10 单物品 itemSubmit 编辑器，并保持旧多物品 itemSubmit 运行时语义。

本阶段以用户手动测试为主，MCP/TestBridge 仅作为辅助工具。截图、报告和自动化输出只能作为参考，最终 UI 是否通过由用户确认。用户确认前不得 checkpoint。

## 前置条件

- 当前分支：`feature/web-admin-unified-item-submit-editor`
- 基线：`v1.40.0-local-test-mcp-foundation`
- 已启动 Minecraft dev client 并进入测试世界。
- WebAdmin 可访问并能以 OWNER 或具备编辑权限的账号登录。
- 目标 VBD 已创建，并能通过右键交互触发测试。
- 不处理 `logs/`，不提交 `reports/mcp`、screenshots、node_modules。

建议准备：

- 一个 VBD 绑定方块。
- 一个测试 channel。
- 一个 receiver 或通过 signal history 观察触发结果。
- 玩家背包中可准备 `minecraft:diamond`、`minecraft:emerald`、附魔书或带自定义名 / Lore / damage / components 的物品。

## 1. 基础显示归属

检查 itemSubmit 是否仍然属于“右键交互条件层”：

- 右键交互启用后，才显示完整 itemSubmit 编辑入口。
- 右键交互未启用时，不显示完整编辑入口。
- 如果已有 itemSubmit 数据但右键交互关闭，应显示 warning，提示数据存在但当前不会作为独立触发源运行。
- WebAdmin 文案不得把 itemSubmit 展示为独立触发源。
- 运行链路应保持：玩家右键 VBD -> 右键交互触发 -> itemSubmit requirement list 判定 -> signal / feedback / runtime result。

失败判定：

- itemSubmit 被显示为独立触发方式。
- 右键交互关闭时仍显示完整编辑入口且没有 warning。
- 文案暗示 itemSubmit 能脱离右键交互独立执行。

## 2. 0 Requirement 状态

准备一个没有 `itemSubmitRequirements[]` 的 VBD，打开 unified itemSubmit editor。

检查：

- 显示“尚未配置提交条件”或等价空状态。
- 只显示“添加提交条件”入口。
- 不显示排序、删除、批量启用 / 禁用、多项列表管理按钮。
- 不显示空槽矩阵。
- 不用一堆空格子代表未配置项。

操作：

1. 点击“添加提交条件”。
2. 确认新增第一个 requirement 后自动选中。
3. 确认 UI 进入 1 requirement 简化状态。

失败判定：

- 0 requirement 时出现上移 / 下移 / 删除 / 批量操作。
- 使用空槽矩阵暗示未配置项。
- 添加后未自动选中新 requirement。

## 3. 1 Requirement 状态

准备或新增 1 个 requirement。

检查：

- 视觉上接近 7.10 单物品提交体验。
- 显示当前 requirement 的模板槽和配置项。
- 不显示多项管理按钮。
- 不显示上移 / 下移。
- 不显示复杂列表滚动按钮或无意义的灰色管理按钮。
- 不显示“多物品提交”误导文案。
- 可以显示“添加另一个提交条件 / 添加条件”入口。

操作：

1. 从玩家背包左键复制一个模板物品，例如 `minecraft:diamond`，确认不消耗真实物品。
2. 调整 count / countMode。
3. 尝试右键清空模板，确认只清空 ghost/template，不影响真实物品。
4. 尝试删除唯一 requirement：默认不应显示删除；如果有清空入口，必须二次确认。
5. 点击“添加另一个提交条件”，确认新增第二个 requirement 后进入多项列表状态。

失败判定：

- 1 requirement 时显示上移 / 下移 / 删除 / 批量操作。
- 删除唯一 requirement 没有二次确认。
- 左键复制模板消耗或移动了真实物品。
- 右键清空影响真实背包物品。

## 4. 2+ Requirements 状态

准备 2 个或更多 requirement。

检查：

- 显示 requirement list。
- 列表可滚动。
- 可选择当前 requirement，右侧详情跟随切换。
- 显示添加 requirement。
- 如本阶段已实现，上移 / 下移仅在 2+ 状态显示，首项不能上移，末项不能下移。
- 删除 requirement 必须二次确认。
- 删除到只剩 1 个 requirement 后，UI 自动回到单物品简化显示。
- 保存时按列表顺序写入 `itemSubmitRequirements[]`。

建议操作：

1. Requirement A：`minecraft:diamond`，countMode=`exactly`，count=3，consumeCount=3。
2. Requirement B：`minecraft:emerald`，countMode=`exactly`，count=2，consumeCount=2。
3. Requirement C：附魔书或带自定义名 / Lore / components 的物品，用于回显测试。
4. 选择 A/B/C，确认详情区正确切换。
5. 删除 C，确认二次确认出现。
6. 删除到只剩 1 个时，确认回到简化 UI。

失败判定：

- 2+ 时没有列表或不能选择当前项。
- 删除不需要确认。
- 删除到 1 个后仍显示多项管理按钮。
- 保存后 requirement 顺序被无故重排。

## 5. 每个 Requirement 字段

逐项检查每个 requirement 可编辑字段：

- `enabled`
- 模板物品
- `countMode`
  - `at_least`
  - `exactly`
  - `at_most`
  - `ignore`
- `count` / `requiredCount`
- matcher options
  - `matchDamage`
  - `matchCustomName`
  - `matchLore`
  - `matchCustomData`
  - `matchComponents`
- `consumeCount`
- tooltip
- display template / `templateDisplayStack`
- 附魔书、components、自定义名、Lore、damage 回显

重点确认：

- `count` / `requiredCount` 是匹配数量。
- `consumeCount` 是消耗数量。
- UI 文案必须清楚区分“匹配数量”和“消耗数量”。
- `matchComponents=false` 时，components 可用于显示但不强制参与匹配。
- `matchComponents=true` 时，按旧 matcher 语义参与匹配。

失败判定：

- 保存后二次打开丢失附魔书、components、自定义名、Lore 或 damage。
- `consumeCount` 被当成 matcher count。
- matcher options 保存或回显错误。

## 6. 全局 ItemSubmit 字段

检查全局字段位于 itemSubmit / 右键交互条件层，而不是单个 requirement 普通模板字段：

- `itemSubmitEnabled`
- `itemSubmitConsumeEnabled`
- `itemSubmitConsumeOrder`
  - `hotbar_first`
  - `main_inventory_first`
- 原版交互策略
  - `allow`
  - `require_item_match`

失败判定：

- 全局 consume 字段被错误放入某一个 requirement。
- 原版交互策略保存后被误重置。
- consume order 保存或回显错误。

## 7. 原子提交 / All-Or-Nothing Consume

必须确认旧多物品语义没有回退：

- 多个 enabled requirements 必须全部满足才成功。
- 只满足部分 requirement 时整体失败。
- disabled requirement 不参与成功条件，但配置和状态要保留。
- `itemSubmitConsumeEnabled=false`：只判定，不消耗。
- `itemSubmitConsumeEnabled=true`：必须先 stage 全部 requirement 的消耗计划。
- 任一 requirement 不满足或 consume plan 失败，不得消耗任何物品。
- 全部 requirement 都满足且 consume plan 全部可 stage 时，才一次性 apply consume。
- 不能出现“前几个 requirement 已经消耗，后一个 requirement 失败”的半提交状态。

建议测试：

1. 配置 requirement A：diamond exactly 3，consumeCount=3。
2. 配置 requirement B：emerald exactly 2，consumeCount=2。
3. 设置 `itemSubmitConsumeEnabled=true`。
4. 玩家只持有 diamond 3，不持有 emerald。
5. 右键 VBD，确认整体失败，diamond 不被消耗。
6. 给玩家 diamond 3 + emerald 2。
7. 右键 VBD，确认整体成功，diamond 和 emerald 按计划一次性消耗。

失败判定：

- 部分满足时发出成功 signal。
- 部分满足时消耗了已满足 requirement 的物品。
- 全部满足时未消耗或只消耗部分物品。

## 8. 保存 / 取消 / 回显

检查：

- 保存后 `itemSubmitRequirements[]` 顺序正确。
- 二次打开完整回显全部 requirements。
- 取消不保存任何未保存修改。
- session / lock / fingerprint 不回退。
- 保存走 WebAdminWriteResult / audit / scoped itemSubmit update。
- WebUI 快照刷新。
- runtime `last*` 字段不被 WebUI 编辑乱写。

建议操作：

1. 打开 editor，修改 requirement A/B。
2. 点击取消，重新打开，确认修改未保存。
3. 再次修改并保存。
4. 重新打开，确认完整回显。
5. 检查 WebAdmin 快照和 inspect/debug 数据。

失败判定：

- 取消后仍保存了修改。
- 保存后 runtime last 字段被清空或被 WebUI 表单值覆盖。
- session lock 未释放。

## 9. 字段保留 / 回归范围

保存 itemSubmit 后检查以下字段不被误改：

- 7.9 native trigger 相关字段保留。
- 7.8 matcher 相关字段保留。
- container `itemConditions` 保留。
- metadata / display metadata 保留。
- consume 字段保留。
- 原版交互策略不被误重置。
- native trigger channel / mode 不被误改。

失败判定：

- 保存 itemSubmit 后 container itemConditions 被清空。
- 设备 metadata、displayName、icon、channel 被误改。
- 7.8 / 7.9 相关配置出现回退。

## 10. 运行时测试

成功路径：

1. 玩家满足多个 enabled requirements。
2. `use_block` 或真实右键 VBD。
3. 期望 itemSubmit 成功。
4. signal / receiver / history 可观察到成功结果。
5. Doctor 无新增 error。

失败路径：

1. 玩家缺少其中一个 enabled requirement。
2. `use_block` 或真实右键 VBD。
3. 期望整体失败。
4. consume enabled=true 时，不消耗任何物品。
5. history / runtime failure reason 指向未满足 requirement。

consume=false：

- 只做判定，不消耗物品。

consume=true：

- 成功后按 staged consume plan 一次性消耗。

原版交互策略：

- `allow`：itemSubmit 失败时允许原版交互继续。
- `require_item_match`：itemSubmit 失败时阻断原版交互。

额外检查：

- signal history。
- receiver 状态。
- doctor issues。
- WebAdmin console errors。
- device runtime last result。

## 11. UI 手动检查

游戏内 GUI：

- 小分辨率：854x480。
- 4K 200% scaled：用户实际 4K 200% 视觉，或当前工具定义的等价窗口 / scale 组合。
- GUI scale：2 / 3 / 4。
- 底部玩家背包和 hotbar 不被按钮遮挡。
- 保存 / 取消按钮可见可点击。
- requirement list 可滚动且不被裁切。
- 当前 requirement 详情不覆盖模板槽。
- tooltip 正常。

WebAdmin：

- 小分辨率：854x480。
- 4K 200% scaled：1920x1080 CSS viewport + deviceScaleFactor 2，或用户真实 4K 200% 视觉。
- VBD 详情页右键交互区域布局正常。
- 统一设备配置 modal 中 itemSubmit 区域布局正常。
- sidebar / topbar / footer 不覆盖关键按钮。
- 不出现横向溢出或内容裁切。

截图规则：

- Codex 可辅助生成截图和报告。
- Codex 必须对截图做明显问题预检：遮挡、按钮覆盖、横向溢出、裁切、关键按钮可见性、明显错位、小分辨率与 4K scaled 差异。
- 每张截图应标记 pass / warning / fail / needs_user_review，并说明 reason。
- Codex 无法直接视觉判断时必须标记 needs_user_review。
- 最终 UI 是否通过仍必须等待用户确认。
- 用户确认前不得 checkpoint。

## 12. 负向边界

确认本阶段没有引入以下能力：

- 没有 ConditionEngine。
- 没有 raw JSON 编辑。
- 没有任意 NBT path 编辑。
- 没有新 consume strategy。
- 没有 inventory / equipment / armor 来源编辑。
- 没有成功 / 失败路径可视化。
- 没有独立新触发源。
- 没有 OS 鼠标键盘操作。
- 没有 Minecraft GUI 坐标点击。
- 没有外网访问。
- 没有任意 shell。
- 没有 git mutation。

## 通过标准

- 0 / 1 / 2 / 3+ requirement 状态均按规则显示。
- 1 -> 2 自动切换到多项列表状态。
- 2 -> 1 自动回到单物品简化状态。
- 多 requirement 保存、回显、顺序和字段保留正确。
- 旧 all-or-nothing / staged consume 语义保持。
- 7.8 matcher、7.9 native trigger、container itemConditions、metadata 无回退。
- 小分辨率和 4K 200% scaled 下无明显布局遮挡或裁切。
- 用户人工确认 UI 后，才允许 checkpoint。
